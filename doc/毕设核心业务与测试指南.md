# 毕设核心业务与测试指南

更新：2026-09-24。按用户最新要求保持简单，目标是能说明业务、跑通主线、完成演示，不把毕设扩展成完整商业物业系统。

## 1. 业务怎么讲

系统有管理端和居民小程序两种入口，AI 是管理端的辅助查询能力。

1. 管理员先建立小区、楼栋、单元、房间，父子归属必须一致。房间入住状态由房间资料维护，关联业主不自动等于入住。
2. 居民用新手机号注册账号；若物业已建档，需物业线下核验后发放 15 分钟一次性激活码，再用原手机号和档案姓名在小程序开通登录。管理端选择相应居民档案与房间提交关联，经物业审核后建立人房关系。没有短信/实名校验，注册不是房屋身份证明；存量空密码档案不能公开认领。
3. 居民提交报修后生成唯一性更好的 RX 雪花编号，状态为待处理。客服派给具备权限的维修人员，维修人员接单、完成。管理员不会自动拥有“替他人接单”的资格。
4. 投诉/建议按待受理 → 处理中 → 已回复 → 已关闭流转；不予受理需要说明原因。当前是一条回复，不是复杂多轮时间线。
5. 居民小程序查看升级后本人提交的工单和结果。姓名和电话是联系资料，不用于新工单的归属判断。
6. AI 查询真实工单、公告、社区资料；权限不足就拒绝，数据未接入就说明。不能演示“真实欠费”“自动执行投诉/报修”等未实现能力。

报修：Pending → Allocated → Processing → Processed；Pending 可取消/拒绝，Allocated 可取消。保持现有六状态，不新增验收返工。

投诉：Pending → Processing → Replied → Closed；Pending 可带原因关闭。

关联：Auditing → Binding / Rejected；已绑定可解绑，审核中可撤回。审核、解绑、撤回留痕，均不修改入住状态。

## 2. 演示准备

- 管理员用于建档、配置角色；客服账号具有报修查询/派单、投诉处理、关联审核权限；维修账号至少具有报修列表、详情、接单、完成权限。
- 主后端使用 JDK 8，端口 8080；MySQL 与 Redis 在线。AI 用 Java 17+，端口 8090；需要模型密钥。无 MCP 时设 MCP_CLIENT_ENABLED=false，否则先启动 8091 的 MCP 服务。
- 前端目录为 D:\Uilted\hjy_ui\hejiayun_ui，Node.js 18+，npm run dev；不是旧 webpack 启动方式。
- 小程序目录为 D:\Uilted\hij_wweixin。开发者工具按 config.js 配置后端；真机不能把 localhost 当电脑地址。
- 配套发布主后端、AI、前端，重新登录。代码提交不等于已部署，当前运行的旧进程也不代表新代码已生效。
- 用专门的演示账号和标注“测试”的房屋/工单，不删除或改造真实居民资料。数据库未执行迁移，原有敏感 SQL 未执行或上传。

## 3. 一次完整演示（约 10–15 分钟）

1. 管理端新增测试小区 → 楼栋 → 单元 → 房间。故意传错小区/楼栋组合，应被拒绝；编辑已有房间不能直接迁移单元。
2. 小程序注册一个未使用的测试手机号并登录。另用测试手机号在后台先建档，物业线下核验后点“开通小程序”，把激活码交给测试居民；居民在小程序注册页填写原手机号、姓名、密码和激活码，登录后确认仍是原业主 ID，重复使用激活码应失败。管理端发起房屋关联并审核通过，检查房间入住状态没有自动变更。
3. 小程序提交“测试：厨房水龙头漏水”，记下 RX 编号。管理端报修列表应看到 Pending。
4. 客服点派单，下拉只显示可接单且可完成的启用人员。指定维修 A；维修 B 不应有接单按钮，直调接单接口也应拒绝。
5. A 登录接单 → 完成；居民刷新“我的报修”，应看到状态变化。重复完成应拒绝。未派给 A 的历史工单不能用 A 强行完成。
6. 居民提交测试投诉；管理端受理 → 回复处理结果 → 关闭；居民查看结果。空回复、跳过状态、重复受理应被拒绝。
7. 解绑测试关联，检查留痕且入住状态不变；不要用这一步证明产权转让或真实搬出。
8. 管理端 AI 输入“帮助”“查一下报修进度”“查询工单 RX…”“最近有什么通知”。中文、空行应正常；输入“欠费多少”应说明未接入账单，不应编金额。清除对话后服务端记忆也清除。

## 4. 必测反例

| 场景 | 预期 |
| --- | --- |
| 普通人员修改用户角色/菜单 | 拒绝；当前要求用户 ID 1 的平台管理员 |
| 停用账号后继续使用令牌 | 下一次认证被拒绝，重新登录也失败 |
| 已建档手机号无激活码注册、错误码或过期码 | 均拒绝，不创建第二条业主档案；已开通或停用档案不能发码 |
| 两个窗口同时审核同一关系 | 只有一方状态更新成功，失败方不新增审核记录 |
| 两个窗口同时接单/回复 | 只有符合原状态的请求成功，另一方提示状态变化 |
| 同人同房并发申请 | 事务内锁房间并检查现有有效关系；需要独立测试库实测竞争 |
| 客户端伪造流程状态、完成人、审核状态 | 新建/普通编辑不能替代动作接口 |
| 修改居民姓名或电话后重新登录 | 新提交工单仍按稳定居民 ID 找回 |
| 同名、部分姓名或通配符 | 不会用于居民本人列表的身份匹配 |
| 查看旧历史单/管理端代录单 | 管理端保留；小程序不自动认领，可能不显示 |
| AI 无权限/业务接口故障 | 提示失败，不说“没有记录”，不换管理员身份重试 |
| 点击立即执行定时任务 | 明确提示执行器未接入，不伪装执行成功 |

物业工作台：物业/客服登录后首页直接展示待审核人房关联、待派单报修、处理中报修和待受理投诉数量；点击卡片或快捷按钮进入对应业务页面。工作台只聚合当前账号有权限读取的数据，派单、接单、完成、审核等动作仍由后端权限和状态机校验。

## 6. 重要边界（答辩时不要过度承诺）

- 新居民工单用 create_by 的 owner:ID 实现提交者隔离，不是完整居民/房屋/社区权限模型；管理端代录单不自动归居民。旧记录原样保留，不按姓名电话迁移。
- 暂无短信归属核验；存量居民激活依赖物业线下核验和手工交付激活码，没有远程实名验证。多社区行级隔离、居民验收返工、消息中心、真实账单支付、门禁和访客进出核验仍未实现。
- 房屋绑定与入住联动已停止，但没有独立入住登记历史。关联撤回/解绑仍移除活动关系，留痕查询入口还不完整。
- 雪花编号消除单实例秒级重号；多实例工作节点配置和数据库唯一索引仍需部署设计，不能声称数据库已强制唯一。
- 父级校验和级联删除尚不能替代外键；数据库缺失索引/历史重复房间不能靠自动猜测修复。
- 当前版本适合本地毕设演示，不宣称商业生产就绪或“所有漏洞已消除”。
