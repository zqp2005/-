# 合家云社区物业管理平台

## 毕设答辩问题与参考答案

> 本文按当前项目实际实现整理。答辩时应区分“已实现功能”和“后续规划”，不要把规划功能描述成已经完成。

## 一、项目概述

### 1. 项目主要解决什么问题？

项目面向社区物业管理场景，统一管理社区、楼栋、单元、房屋、居民档案、报修、投诉建议和访客等信息。管理员通过后台维护物业数据，居民通过微信小程序注册、绑定房屋、提交和查询服务工单，从而减少人工登记并提高处理过程的透明度。

### 2. 为什么选择这个题目？

传统社区物业服务中，居民资料、房屋关系和报修记录容易分散在纸质表格或多个系统中，查询和跟踪效率较低。本项目将物业基础数据、居民服务和智能助手整合到一个平台，具有明确的实际应用场景，也能体现前后端分离、权限控制、数据库设计和业务流程设计能力。

### 3. 项目的核心业务流程是什么？

1. 管理员建立社区、楼栋、单元、房屋和居民档案。
2. 居民通过小程序注册，或使用物业发放的激活码开通账号。
3. 居民提交房屋绑定申请，物业审核绑定关系。
4. 居民提交报修或投诉建议。
5. 物业人员受理、派单、接单、处理并完成工单。
6. 居民在小程序查询自己的房屋、报修和投诉信息。

## 二、技术架构

### 4. 项目采用什么架构？

项目采用前后端分离架构：

- Vue 2 和 Element UI：后台管理端。
- 微信小程序：居民服务端。
- Spring Boot：后端 REST 服务。
- MySQL：结构化业务数据存储。
- Redis：令牌、激活码和 AI 会话记忆存储。
- Spring AI 和 DeepSeek：智能助手。
- MCP Server：登录地址定位和天气查询工具服务。

### 5. 为什么使用 Spring Boot？

Spring Boot 适合快速构建 REST 服务，自动配置能力强，能够方便集成 Spring Security、MyBatis-Plus、Redis、Swagger 和事务管理等组件，适合本项目的多业务模块结构。

### 6. 为什么使用 MySQL？

社区、楼栋、房屋、居民和工单之间存在明确的结构化关系。MySQL 支持事务、索引、唯一约束和复杂关联查询，适合保存这类关系型业务数据。

### 7. Redis 在项目中有什么作用？

Redis 用于保存管理端和居民端登录令牌、短期激活码摘要、激活过程中的并发锁以及 AI 会话记忆。激活码只保存摘要，不保存明文，且具有过期时间。

## 三、数据库设计

### 8. 居民信息存储在哪里？

居民信息存储在 `hjy_owner` 表，包括姓名、手机号、身份证号、密码和启用状态等字段。居民和房屋之间通过居民-房屋关联表建立关系。

### 9. 为什么使用居民-房屋关联表？

居民和房屋在业务上不是简单的一对一关系，一个居民可能关联多个房屋，一个房屋也可能存在多个合法关联人。因此使用关联表可以保存绑定状态、审核结果和操作时间，便于后续扩展。

### 10. 如何避免手机号重复？

服务层在新增和修改居民档案时检查手机号是否已经属于其他档案；数据库通过手机号唯一索引进行并发兜底。历史重复数据不能根据姓名自动猜测归属，必须人工核对后再处理。

### 11. 为什么不根据姓名或手机号认领报修单？

姓名和手机号可能重复，使用它们认领工单容易造成数据串户。新工单使用稳定的居民 ID 记录创建人，小程序查询时按当前居民 ID 精确查询。

## 四、权限与安全

### 12. 项目有哪些用户角色？

后台包含管理员和物业工作人员等角色；居民使用小程序端账号。后台账号和居民账号使用相互独立的认证流程，居民端不会直接获得后台管理权限。

### 13. 管理员和普通用户有什么区别？

管理员可以进行用户、菜单和物业业务管理；普通后台用户只能访问被授予的菜单和接口。居民账号只能访问小程序端接口，例如查看自己的房屋和工单。

### 14. 如何保证接口安全？

后台接口使用 JWT 和 Spring Security 进行认证授权；小程序使用独立的居民 JWT，并在 Redis 中维护令牌状态。服务端会校验令牌、账号状态和有效期，接口还通过方法级权限控制限制操作范围。

### 15. 激活码如何防止泄露和重复使用？

系统不保存激活码明文，只保存摘要。激活时先用 Redis 原子脚本短时预留激活码，数据库写入密码成功后再删除激活码；数据库写入失败会释放预留锁，原码在有效期内可以重试。重新发码和激活过程互斥。

### 16. 为什么不能仅凭姓名和手机号激活已有档案？

姓名和手机号不足以证明当前操作者就是档案本人，直接开放会产生冒用风险。因此已有居民档案需要物业线下核验后，由物业发放短期激活码。

## 五、核心业务设计

### 17. 报修工单有哪些状态？

报修通过动作接口驱动状态流转，主要包括待处理、已派单、处理中、已完成、已取消和已驳回等状态。具体可执行动作由当前状态决定。

### 18. 为什么要设计状态机？

如果允许前端直接修改状态，可能出现未派单直接完成、已取消后重新接单等非法情况。状态机把业务流转限制在合法路径内，并自动记录操作人和时间。

### 19. 居民绑定房屋后为什么还要审核？

居民填写的信息不一定真实，房屋绑定关系又会影响居民可查询的数据范围。因此绑定申请需要物业审核，审核通过后才成为有效关联。

### 20. 物业人员如何处理报修？

管理员查看待处理工单后，将工单派给具有接单权限的物业人员。物业人员接单并处理，完成后填写处理结果，居民可以在小程序查看状态和处理进度。

## 六、AI 与 MCP 模块

### 21. AI 模块可以做什么？

当前 AI 可以辅助查询当前账号有权限访问的报修、投诉、居民、房屋、社区和公告信息，也可以通过 MCP 查询登录地址和天气。AI 查询结果仍受主后端权限控制。

### 22. AI 是否拥有管理员权限？

没有。AI 服务只透传当前调用者的令牌，调用主后端时使用的仍是当前账号身份。当前账号没有权限访问的数据，AI 也不能越权访问。

### 23. AI 记忆如何保存？

AI 对话记忆保存在 Redis，使用稳定的会话 ID 作为键，并限制消息窗口大小。只要 Redis 中的数据仍然存在，服务重启后可以继续使用该会话记忆。

### 24. AI 为什么不能直接随意创建报修单？

创建报修属于写操作，误识别会产生真实业务数据。目前设计为先整理报修信息并要求用户确认，最终提交时沿用当前账号权限，避免 AI 越权或误提交。

### 25. MCP 是什么？

MCP 是 AI 调用外部工具的一种协议。本项目通过独立 MCP Server 向 AI 提供登录地址定位和天气查询工具，AI 根据用户问题决定是否调用对应工具。

## 七、测试与部署

### 26. 做了哪些测试？

测试覆盖居民注册、登录、令牌隔离、激活码生成和失败重试、重复手机号校验、Mapper 配置、用户资料接口、会话撤销等内容。当前主后端完整测试共 67 项通过。

### 27. 如何验证核心功能？

1. 创建社区、楼栋、单元、房屋和居民档案。
2. 为启用且有手机号的居民生成激活码。
3. 在小程序输入激活码并设置密码。
4. 提交房屋绑定申请，在后台审核绑定。
5. 提交报修，后台派单、接单并完成。
6. 在小程序查询报修进度。
7. 使用不同角色登录，验证菜单和接口权限。
8. 使用 AI 查询，确认结果只包含当前账号可访问的数据。

### 28. 项目如何部署？

主后端默认运行在 8080 端口，AI 服务运行在 8090 端口，MCP Server 运行在 8091 端口，前端开发服务器通常使用 80 端口。部署前需要配置 MySQL、Redis、JWT 密钥和 DeepSeek API Key，并按环境执行数据库迁移。

## 八、项目不足与改进方向

### 29. 项目目前有哪些不足？

当前暂未实现完整收费账单、消息通知中心、报修验收与返工、复杂物业服务范围控制、短信实名核验和独立入住登记历史等功能。这些属于后续扩展，不影响当前毕设核心流程。

### 30. 如果继续完善，优先做什么？

优先完善报修闭环，增加居民验收、返工和评价；之后增加消息通知和物业人员服务范围控制，最后再扩展收费、统计分析和移动端推送。

### 31. 项目的创新点是什么？

项目的主要特点包括：后台管理端与居民小程序分离；居民账号与后台账号独立认证；通过激活码安全衔接物业档案和小程序账号；AI 查询沿用当前用户权限；通过 MCP 扩展定位和天气工具；报修和投诉使用状态机约束流转。

### 32. 项目有什么实际价值？

项目可以减少物业人工登记工作，提高报修处理透明度，让居民及时查看工单进度。统一的社区、房屋和居民数据也能提高物业查询和管理效率，AI 助手可以降低常用业务信息的查询成本。

## 九、答辩表达建议

- 先说明项目目标，再说明技术实现，最后说明验证方式。
- 对未实现功能明确说“当前范围暂未实现，计划作为后续扩展”，不要夸大系统能力。
- 遇到安全问题，重点回答身份隔离、权限校验、数据范围和并发控制。
- 遇到项目不足，先承认边界，再说明为什么当前毕设范围优先保证建档、关联、报修和查询闭环。
