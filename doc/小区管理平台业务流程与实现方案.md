# 第一部分：业务流程讲解

## 0. 平台全景

平台四个模块互相咬合，构成一条完整主线：

```
房产台账              人房挂钩                日常事务                    数据保护
（小区→楼栋→单元→房间） →（业主绑定房屋·审核） →（报修工单 / 投诉处理） →（删除前的级联校验）
  房子怎么进来           人怎么合法住进来         住进来之后的事怎么办          台账不被误删
```

现状问题：四块全是纯增删改查——状态字段存在但能随意改、审核流程后端写了一半前端没接、删除不检查下级数据。本次改造就是把"业务规矩"补进这四块。

## 1. 报修工单流程

**场景**：业主家水管漏了，物业登记一条报修记录（即"工单"，工单号 `repair_num` 相当于快递单号），之后工单在物业内部一步步流转，直到修完或明确不修。

```
                     ┌──── cancel(取消) ────┐
                     ▼                      │
Pending ──assign(派单)──> Allocated ──receive(接单)──> Processing
(待处理)                 (已分派)                 (处理中)
   │                        │                        │
   │cancel                  │cancel                  │complete(完成)
   ▼                        ▼                        ▼
Cancelled              Cancelled                 Processed(已处理)
(已取消)                 (已取消)
   │
   └─reject(不处理)──> No_Processed(不处理)

终态（任何操作都不再允许）：Processed、No_Processed、Cancelled
```

**每一步自动留痕**（字段都是表里现成的）：

| 动作 | 谁操作 | 状态变化 | 系统自动记录 |
|------|--------|---------|-------------|
| 新增报修 | 客服 | → Pending | 自动生成工单号（RX+日期+序号）、登记人 |
| 派单 | 客服 | Pending → Allocated | 派单时间、所选维修人 |
| 接单 | 维修工 | Allocated → Processing | 接单时间 |
| 完成 | 维修工 | Processing → Processed | 完成时间、完成人姓名/ID/电话（取当前登录人） |
| 取消 | 客服 | Pending/Allocated → Cancelled | 取消时间、取消原因 |
| 不处理 | 客服 | Pending → No_Processed | 不处理原因 |

**规矩**：
1. 不按图上的箭头走就拒绝（如对"已处理"的工单派单 → 提示"工单已是【已处理】状态，无法派单"）
2. 状态、各时间戳、维修人等流转字段**只能由动作接口修改**；普通"编辑"只允许改报修内容、地址、备注
3. `door_time`（上门时间）不纳入自动流转，由编辑接口手动补录

## 2. 投诉建议处理流程

**场景**：业主投诉噪音/卫生等问题，物业受理、处理、给回复，最后关闭。投诉要让业主"有回音"，不能石沉大海。

```
Pending ──accept(受理)──> Processing ──reply(回复)──> Replied ──close(关闭)──> Closed
(待受理)                  (处理中)                    (已回复)                (已关闭)
   │                                                                            ▲
   └────────────────────── close(不予受理，填原因) ────────────────────────────┘
```

| 动作 | 状态变化 | 系统自动记录 |
|------|---------|-------------|
| 受理 | Pending → Processing | 处理人（当前登录人）、处理时间 |
| 回复 | Processing → Replied | 回复内容（需填写） |
| 关闭 | Pending/Replied → Closed | 关闭原因（Pending 直接关闭时必填，写备注） |

**规矩**：已回复的投诉只能关闭，不能再受理/回复；本次不做"重新打开"（reopen），保持流程简单。

## 3. 业主入住绑定流程

**场景**：业主/租户要挂到某套房间上（"张三是 3栋2单元501 的业主"）。现实中物业要核验房产证明，所以绑定不能直接生效，要审核。这是系统里唯一已有半成品流程的模块（`auditOwnerRoom` 方法、审核记录表都在，前端没接）。

```
新增绑定（人+房+身份）
        │
        ▼
  Auditing(审核中) ──审核通过──> Binding(已绑定) ──解绑──> 记录留痕，绑定删除
        │                        │
        └──审核驳回──> Rejected(已驳回，留痕)  └─联动：房间状态自动变"已入住"
                                              （解绑后若房间无人，自动变回"未入住"）
```

**规矩**：
1. 新增绑定的状态一律是"审核中"，前端传什么状态都忽略
2. 同一房间 + 同一人不能重复绑定（已驳回的除外，可以重新提交）
3. 审核必须填意见；通过/驳回都往审核记录表（`hjy_owner_room_record`）插一条留痕（谁审的、什么时候、什么意见）
4. "审核中"的记录可直接撤销删除（相当于撤回申请）；"已绑定"的删除即为**解绑**（退房），解绑会留痕并触发房间状态联动
5. 房间状态联动：绑定通过 → 房间自动"已入住"；解绑后该房间再无任何"已绑定"的人 → 自动"未入住"

**人员身份**（沿用现有字典 `hjy_owner_state`）：yz 业主 / zh 租户 / qs 亲属 / qt 其他——一套房可挂多人（如业主+租客同时挂），一人可有多套房。

## 4. 数据保护：级联删除校验

**场景**：防止把"还挂着人的房子"或"还有楼的小区"删掉，造成孤儿数据和台账混乱。

| 删除目标 | 删除前检查 | 有数据时 |
|---------|-----------|---------|
| 小区 | 社区下还有楼栋？ | 拒绝："小区【××】下存在 N 栋楼栋，无法删除" |
| 楼栋 | 楼栋下还有单元？ | 拒绝（同构提示） |
| 单元 | 单元下还有房间？ | 拒绝（同构提示） |
| 房间 | 房间还有业主绑定（非驳回）？ | 拒绝："房间存在业主绑定关系，无法删除" |
| 业主 | 业主名下还有绑定房屋？ | 拒绝："业主【××】名下存在绑定房屋，无法删除" |

只查**直接下级**（间接数据会被层层挡住）。批量删除逐条检查，**任一存在下级则整批拒绝**（不做部分删除，行为可预期）。

## 2. 后端改动（hjy-community）

### 2.1 公共部分

- 新增业务异常使用方式与现有 `ServiceException`（common.core.exception）一致，非法流转直接抛出，由 `GlobalExceptionHandler` 统一转成失败响应

### 2.2 报修模块（`property` 包 + `web.controller.system.HjyRepairController`）

**新增常量类** `property/constant/RepairState.java`：六个状态值 + 合法转移表（`Map<当前状态, Set<目标状态>>` 或枚举实现），供校验复用。

**HjyRepairService 新增方法**（每个方法内部三步：查旧状态 → 校验转移合法 → 更新状态并补时间戳/操作人）：

| 方法 | 转移 | 写入字段 |
|------|------|---------|
| `assignRepair(repairId, assignmentId)` | Pending→Allocated | assignment_time=now、assignment_id |
| `receiveRepair(repairId)` | Allocated→Processing | receiving_orders_time=now |
| `completeRepair(repairId)` | Processing→Processed | complete_time=now、complete_id/name/phone=当前登录人（phone 查 sys_user） |
| `cancelRepair(repairId, reason)` | Pending/Allocated→Cancelled | cancel_time=now、remark 追加原因 |
| `rejectRepair(repairId, reason)` | Pending→No_Processed | remark 追加原因 |

**改造现有方法**：
- `insertRepair`：repair_num 为空时自动生成（`RX` + yyyyMMdd + 4 位当日序列）；状态强制 Pending
- `updateRepair`：流转字段（repair_state、各时间戳、assignment_id、complete_*）从入参中**忽略**，仅更新 repair_content、address、remark、door_time
- 对应 Controller 新增 5 个 PUT 端点：`/system/repair/assign/{id}` 等

### 2.3 投诉模块（`HjySuggestController` / `HjySuggestServiceImpl`）

- Domain/VO/Mapper 增加 4 个新字段映射；列表查询支持按状态筛选
- Service 新增：`acceptSuggest(id)`、`replySuggest(id, replyContent)`、`closeSuggest(id, reason)`
- Controller 新增 3 个 PUT 端点：`/system/suggest/accept/{id}`、`/reply/{id}`、`/close/{id}`
- `updateSuggest` 同报修降级：只允许改内容类字段，状态字段忽略

### 2.4 绑定模块（`HjyOwnerRoomController` / `HjyOwnerRoomServiceImpl`）

- `insertOwnerRoom`：状态强制 `Auditing`；查重（同 room_id + owner_id 且状态 ≠ Rejected 存在即拒绝）
- `auditOwnerRoom`（改造现有方法）：入参 `{auditResult: pass|reject, auditOpinion}`；校验当前状态必须 Auditing；pass → Binding + 插 record(type=pass) + 联动房间 `room_status=has_stay`；reject → Rejected + 插 record(type=reject)；审核人取当前登录人
- 删除升级为解绑语义：仅 Binding/Auditing 可删；Binding 删除时插 record(type=unbind)；删除后若该房间无其他 Binding 记录，联动 `room_status=none_stay`
- Controller：新增 `PUT /system/ownerRoom/audit/{id}`；DELETE 端点沿用

### 2.5 级联删除校验（5 个 ServiceImpl 的 delete 方法前置检查）

- `HjyCommunityServiceImpl`：count 楼栋
- `HjyBuildingServiceImpl`：count 单元
- `HjyUnitServiceImpl`：count 房间
- `HjyRoomServiceImpl`：count 绑定（状态 ≠ Rejected）
- `HjyOwnerServiceImpl`：count 绑定（状态 ≠ Rejected）
- 批量删除（deleteByIds）循环校验，任一命中即抛异常整批拒绝，提示中带具体名称/数量

## 1. 现状审计：发现的问题

### A 类：架构级问题（必须修）

| # | 问题 | 证据 | 后果 |

| C2 | AI 以 admin 身份调主后端 | 工具含创建报修/投诉等写操作，权限过大；理想是建专用低权限账号 |
| C3 | 健康检查太浅 | `/ai/health` 恒返回 OK，不探活主后端/DeepSeek |

## 2. 改动方案（按优先级分档）

### P0：修复（与业务流程改造同期做）

1. **统一调用链**：`ChatController.chat()/chatStream()` 全部改走 `ChatService`；流式逻辑从 Controller 下沉到 `ChatServiceImpl.chatStream()`（含空消息/问候/帮助拦截、用户信息注入），删除 Controller 里的重复 `.tools()` 注册
2. **401 重试**：`HjyCommunityClient` 各请求方法检查响应状态，401/403 时清空缓存 token → 重登 → 重试一次；仍失败返回明确错误 JSON（`code:401`），工具侧识别后告知用户"物业系统连接异常"而非"未查到"
3. **删除死代码**：整个 `agent/` 包、`dto/KnowledgeRequest`、`model/` 空包、`PromptTemplate` 中无引用的构建方法
4. **与业务流程改造的衔接确认**（无需改 AI 代码）：`RepairTool.createRepairOrder`（POST /system/repair）与 `ComplaintTool.submitComplaint`（POST /system/suggest）在主后端改造后自动兼容——状态由后端强制置初始值、工单号后端生成；查询类工具走 list 接口，新增的状态字段会自然带回给 AI 展示

### P1：结构优化

5. **会话记忆 Redis 持久化**：实现 Spring AI 的 `ChatMemoryRepository` 接口（Redis hash 存每个 conversationId 的消息列表，保留窗口 20 条），替换默认内存实现；重启不丢会话，`RedisConfig`/Redis 依赖物归其主
6. **提示词外置**：系统提示词移到 `src/main/resources/prompt/system-prompt.txt`，`ChatClientConfig` 启动时读入；顺带把与 `agent/SystemPrompt.java` 重复的内容一并消灭
7. **SSE 结束标记**：流正常完成时补发 `data: [DONE]\n\n`（需前端 AiChat 组件配合判断）

### P2：增强（默认不做，勾选才做）

8. AI 服务 API Key：`X-Api-Key` 请求头校验（拦截器实现），前端代理层配同一 Key
9. 主后端建 AI 专用账号（仅查询+报修/投诉写入权限），替代 admin 凭据
10. 健康检查增强：`/ai/health` 实际探活主后端 `/captcha` 与 DeepSeek API 连通性
11. 工具假数据诚实化：单价挪到 `application.yml`（`hjy.ai.fee.*`）；欠费/缴费历史两个工具改为返回"账务数据暂未接入，请联系物业服务中心"（等将来做账单模块再接真数据）
