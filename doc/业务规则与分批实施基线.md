# 合家云业务规则与分批实施基线

确认日期：2026-09-24。本文区分已确认的目标规则和已落地代码，不把规划当作现有能力。

## 一、定位与边界

面向多个小区的物业服务平台，以房屋、居民、服务工单为核心，连接管理端与居民小程序。AI 仅作为调用已有业务能力的辅助入口。

主线：房屋建档 → 居民认证与房屋关联 → 报修/投诉 → 物业处理 → 居民确认与反馈 → 待办与统计。

本基线调整 2026-09-10 方案中“纯管理端流转”和“绑定即入住”的定位；未迁移代码仍按原实现运行，不能仅凭本文判断部署能力。

## 二、已确认的核心规则

### 账号、居民、人房关系、入住相互独立

- 登录账号决定谁在操作；居民档案表达人员信息；人房关系表达产权人、租户、家属等身份；入住登记表达实际居住情况。
- **房屋关联不等于入住。** 绑定审核通过不应推断已入住，解除关系不应直接修改销售或交付状态。
- 一人可以关联多套房，一套房可以关联多人；人房身份属于具体关系，不是人员的全局属性。
- 租户关系支持有效期；到期、解除保留历史。房屋转让不能把原住户的私人投诉、联系方式等自动开放给新住户。
- 联系电话与姓名可以变更，不能作为工单归属的主键。保留稳定居民 ID，联系方式仅作为业务快照。
- 房屋、单元、楼栋、社区必须来自同一归属链；父级迁移需要明确动作与事务处理，不能任意修改冗余 ID。

### 居民认证与我的房屋

- 公开注册不能凭手机号认领存量档案。
- 目标流程：注册 → 提交关联申请 → 物业核验 → 通过/驳回 → 我的房屋 → 关系到期/解除。
- 暂无短信服务时，后续实现物业核验后的限时一次性激活凭证；核验材料、办理人、有效期规则需在实施时细化。
- 核验完成前不能把自填姓名、手机号视为可信房屋归属证明；不开放完整业主名单供外部枚举。
- 停用、删除、改密应使已有登录态失效。当前首批只完成禁止停用账号重新登录，旧令牌撤销另批实施。

### 报修与投诉闭环

- 报修目标：待派单 → 已派单 → 处理中 → 待验收 → 已关闭；未解决返回处理中并保留历次处理记录。
- 工单关联居民、社区；私人房屋报修关联房屋，公共区域报修允许无私人房屋关联。
- 代录工单区分操作人、服务对象和来源；迁移时无法确认归属的历史工单不得随意匹配给居民。
- 维修人员只处理分配给自己的工单；主管转派需要原因。处理完成需有说明，居民确认后关闭。
- 投诉采用居民补充、物业回复的时间线，区分内部备注和居民可见内容，支持主管复核。
- 第一阶段不默认超时自动验收；先做提醒。评价时限、重新打开时限在对应批次定义。
- 并发状态变更只有一个请求成功，重复提交不能重复执行动作；终态资料以留痕更正代替随意删除。

### 权限和 AI

- 同时检查动作权限、社区数据范围、记录归属。前端按钮不是安全边界。
- 平台管理员负责账号与授权配置；小区主管、客服、维修人员、居民分别按职责和所属数据范围操作。
- 首批账号/角色/菜单写操作采用平台管理员限制作为临时防线；精细化授权委派与社区数据范围后续实现。
- AI 无独立超级权限，不得把服务账号的权限授予所有对话用户。写操作需可信身份、业务授权和明确确认。
- 没有真实账单时不能生成确定的欠费金额、欠费月份。

### 待办、消息与可选扩展

- 认证申请、派单、完工验收、投诉回复和超时产生待办/站内消息；消息状态不是业务完成状态。
- 消息失败可重试，不能因此重复审核或重复派单。微信订阅消息后续接入。
- 收费后续按“规则 → 账单 → 线下收款登记 → 核销 → 欠费查询”建设；责任主体、周期、规则版本须先确认，历史账单保存快照。
- 访客预约/核验在存在真实保安办理入口后实施；首阶段不扩展商城、停车和门禁。

每批必须：说明行为变化 → 编写正反例测试 → 验证兼容调用方 → 更新对应 README → 仅提交本批文件并推送 → 报告完成项与未完成项。

典型反例：跨小区操作被拒绝；普通用户不能改角色；重复审核仅成功一次；停用账号失效；更改手机号不丢历史工单；房屋绑定不改变实际入住。

后端、前端分别在当前非 dev 分支提交推送；未经要求不动 dev；小程序不提交推送。保留用户原有未提交修改。数据库修复须独立核验、备份并记录迁移/回退步骤，不和功能提交混做。
